How it works under the hood

Base class (barely changes)
abstract class SelvagenModuleComponentBase
{
  abstract string ModuleTable; // "topography"
  abstract Dictionary CollectValues();

  // SolveInstance unchanged:
  // 1. Find or create row for (table, projectId)
  // 2. PATCH with CollectValues()
  // 3. Output RecordID + Status
}
Example: TopoSlopeComponent
class TopoSlopeComponent : ModuleComponentBase
{
  ModuleTable => "topography";

  RegisterInputParams() {
    // ProjectID + 5 slope fields + Upload
    // = 7 inputs total
  }

  CollectValues() => {
    "slope_mesh_id",
    "slope_ref",
    "slope_min", ...
  }
}

Properties component — which module does it target?

Since Properties is standalone, it needs to know which module table to PATCH

A

Dropdown selector input

A dropdown input with choices: Topography, Geology, Analyses, Optimizations. Same pattern as the existing Client/Project selectors you already have.

B

Text input for module name

Simple text input where user types "topography", "geology", etc. Least code but no guardrails against typos.

C

Four separate Properties components

Topo Properties, Geo Properties, etc. — each hardcodes its module table. More components but zero ambiguity, consistent with the "explicit on canvas" philosophy.
