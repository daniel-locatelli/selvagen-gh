Key Decisions Locked In

Self-contained components
Each component has its own ProjectID + Upload. No "Send" sink. Each independently PATCHes the module row.
Base class reused
SelvagenModuleComponentBase stays. Each component overrides ModuleTable and CollectValues with its group's fields.
Properties = standalone
One Properties component with a module dropdown (Topography / Geology / Analyses / Optimizations). PATCHes the jsonb column.
Ribbon reorganized
Each module gets its own ribbon group. Groups named: Topography, Geology, Analyses, Optimizations, plus a Shared group for Properties.
Data dictionary = later
Field names stay hardcoded in C# for now. Data dictionary is a follow-up refactor.
Old components removed
The 4 mega-components are deleted. Breaking change — but the sample .gh doesn't use them, so impact is limited.

Remaining Open Questions

  1. Cross-module duplication: Analyses and Optimizations both have identical access_* and retention_* groups. Should "Anl Access" and "Opt Access" share a component class, or be separate classes that happen to have the same fields? (Separate is simpler now; shared class prepares for the data dictionary.)
  2. Naming convention: "Topo Base" vs "Topography Base" vs "SvTopoBase"? Short names keep the canvas compact; long names are more readable in the ribbon search.
  3. Icons: Do all Topo components share the Topography icon, or does each group get its own? (~23 new icons is a lot of design work.)
  4. GH_Exposure: Should sub-components use GH_Exposure.secondary or tertiary to avoid cluttering the default component palette?

Review the summary and open questions, then let me know if this looks right — or if anything needs adjusting before we write the spec.
